# Machine Builder

You design and build hard-surface machines — mechs, tanks, wheeled vehicles, hovercraft, helicopters, aircraft/VTOL, turrets and emplacements — as rigid parts on an armature, generated by Blender scripts from a reusable kit and an engineering spec.

One job: the MODEL. Animation and damage states belong to downstream tooling; this skill hands it a clean contract (section 9). Environment is out of scope.

Core idea: concept art is a picture, not a machine. The source of truth is the spec: skeleton, joints and their ranges, parts with a function, hardpoints. Geometry is generated from the spec and must pass automated tests before it is detailed.

Never use image-to-3D output (Tripo and similar) as final geometry. At most as a visual reference.

## Prerequisites

- Blender 4.2 or later run headless (tested on 5.2). Find it as `blender` on PATH, the `BLENDER` environment variable or the standard install location (macOS: `/Applications/Blender.app/Contents/MacOS/Blender`); verify with `--version`. PyYAML inside Blender's Python for `.yaml` specs, or pass a `.json` copy.
- Optional: an image-generation tool for `refine`/`generate` concept modes (see Phase 1 for working without one).
- Optional: the `art-direction-pass` skill (shared `docs/art/direction/` format).
- The skill's resources, installed with it under `.claude/skills/machine-builder/` (other tools use their own skills directory): the skill's own `assets/spec.example.yaml` and `scripts/validate.py`. Invoke them by path from the project root.

## Git

Follow the project's own Git rules. The workflow commits once per phase and per kept review iteration: if the project's instructions require approval for commits, ask once at the start. Never push, and never commit changes this run did not make.

Without permission, or when the working tree already has the user's own changes, use snapshots instead of commits. A snapshot is a tree object written through a temporary index; it creates no commit, ref or tag and leaves the project's index alone. `docs/art/` is excluded so reverts never touch the records:

```sh
snap() { idx=$(mktemp); GIT_INDEX_FILE=$idx git read-tree HEAD && GIT_INDEX_FILE=$idx git add -A -- . ':!docs/art' && GIT_INDEX_FILE=$idx git write-tree; rm -f "$idx"; }
```

- Baseline: `snap` before any change; record its id and `git rev-parse HEAD` in `docs/art/units.md`. The user's uncommitted and untracked files are part of it.
- Kept phase or iteration: `snap` again and record the id with the phase's outputs and files in `units.md`.
- Revert: `snap` the current state as `<cur>`, run `git diff --binary <cur> <last kept> | git apply --binary` (this also deletes files the step added), then check that a fresh `snap` equals `<last kept>`. Never use tree-wide `checkout`, `reset`, `clean` or `stash`.

## 0. Arguments

Defaults in brackets. Read them from the invocation text.

- `unit` — id, e.g. `striker_03`.
- `brief` — role, class/weight, faction, style references, intended games/cameras. Can be a few lines.
- `concept` — image(s), optional.
- `concept_mode` [auto] — `provided` (use the concept as is, after engineering review), `refine` (clean up the user's concept with image generation), `generate` (create concepts from the brief). Auto: `provided` if a clean concept exists, `generate` if none.
- `profile` [auto] — `walker` (biped, reverse-joint, quad, hexapod), `tracked`, `wheeled`, `hover`, `rotorcraft`, `fixed_wing` (incl. VTOL), `static` (turrets, emplacements).
- `quality` [hangar] — `hangar`: LOD0 must survive close-up inspection in a hangar view, plus gameplay LODs. `gameplay`: gameplay LODs only.
- `max_iterations` [5] for the review loop.

## 1. Shared foundations (once per project, extended by every unit)

Check and create if missing:
- `docs/art/direction/50-characters.md` (the `art-direction-pass` category-file format: role, shape language, proportions, detail hierarchy, material presets, palette slice, readability, asset spec, Do/Don't, Uncertain), with a **Machines design language** section: bevel widths per part size, chamfer angles, armour plate thickness, panel size and panel-line rules, joint-type catalogue, colour blocking, decal rules (numbers, stripes, insignia), wear level, emissive rules, scale references (cockpit hatch, ladder rung, human pilot 1.8 m).
- `tools/blender/units/kit/` — parametric part library: armour plates, joint housings, actuators and pistons, hydraulic lines, weapon pods (missile racks, cannons, lasers, gatlings), sensors and cockpits, vents and heat sinks, feet and toes, hands, wheels, road wheels and track links, rotors, nozzles, landing gear, hatches, ladders, antennas. One script per family, parameters at the top, deterministic with `--seed`.
- `docs/art/units.md` — registry of all units: id, profile, class, thumbnail, status.

If the project has no design language yet, derive it from the first unit's concept, write it down, and keep it for every next unit. Consistency across units matters more than the beauty of one unit: everything must look like it came from the same factories.

## 2. Phase 1 — Concept

Concepts serve the design; they are never the final word on mechanics.

**Engineering review** (all modes) — annotate the concept with keep / remove / change:
- every visible part must have a function: armour, actuator, weapon, sensor, cooling, ammo, power, access;
- every joint must be able to move through the range its motions need and have something that drives it;
- armour must not block joints at the extremes;
- contact parts (feet, wheels, tracks, gear) must plausibly carry the mass;
- remove decorative gears, impossible joints, floating parts, details that change between views.

**provided** — run the review, write the result to `assets/units/<id>/concept-review.md`, go to Phase 2.

**refine** — run the review, then use image generation (edit mode) to produce a cleaned concept and a turnaround. Keep the user's design intent; change only what the review flagged.

**generate** — from the brief:
1. 6–9 silhouette thumbnails (solid black on white, same scale, side and three-quarter views).
2. Checkpoint: the user picks 1–2 (if unattended, pick by silhouette distinctiveness against existing units in `units.md` and note why).
3. Design sheet of the pick in colour.
4. Turnaround.

Image generation: use whatever is available (the tool's built-in image generation, an image MCP, another tool). If nothing is available, write the prompts to `assets/units/<id>/concept-prompts.md` and ask the user to run them. If unattended, mark the concept as pending in `units.md` and continue from the brief: the spec stays the source of truth, silhouettes are checked against the brief and existing units, and the reviewer gets the brief instead of a concept.

Prompt templates (adapt; keep "no text" — generated lettering is noise):

```text
THUMBNAILS: Sheet of 8 distinct silhouette thumbnails of a {class} {profile} combat machine, {role}.
Solid black silhouettes on white, same scale, side view and three-quarter view, grounded stance,
functional engineering: every joint can move, no decorative gears. Style: {design language summary}. No text.

DESIGN SHEET: Industrial concept of the {class} {profile} machine from the chosen silhouette, three-quarter view,
neutral grey studio background, soft light. Painted armour plates with chamfered edges, visible actuators at joints,
{weapons}. Plausible mechanics only. Matches: {design language summary}. No text, no logos.

TURNAROUND: Orthographic turnaround of the same machine: front, side, back, top. Identical scale and design in all
views, aligned on one ground line, neutral background, flat even light, no perspective, no text.
```

## 3. Phase 2 — Spec

`assets/units/<id>/spec.yaml` — the single source of truth. Start from the skill's `assets/spec.example.yaml` (a walker; other profiles in section 10). Top-level keys: `unit`, `profile`, `class`, `dimensions_m`, `mass_t`, `design_language`, `skeleton` (bone → parent, `rom` per axis, `joint`), `parts` (id, bone, location, function, kit, params, `drives`, `contact`), `hardpoints`, `fx_sockets`, `paint_schemes`, `budgets`, `test_poses`, `sweeps`, `allowed_contacts`, `min_support_margin_m`, optional `ground_check`. Rotations are Euler XYZ in Blender bone-local space; Y runs along the bone (twist).

Location tags (`location`) group parts for the damage skill: walker `hd, ct, lt, rt, la, ra, ll, rl`; vehicles `front, left, right, rear, turret, rotor` — pick a set per profile and keep it consistent across units.

Spec review before modelling: every part has a function, every joint has an actuator part, ROM covers the motions in section 10, armour does not obviously block joints, mass is plausible for the contact area.

## 4. Phase 3 — Skeleton and blockout

1. Generate the armature and a blockout (one simple volume per part, true dimensions) from the spec with a script: `tools/blender/units/build_unit.py --spec ... --stage blockout`.
2. Run `validate.py` (template below). All tests must pass before detailing.
3. Silhouette check: render solid-black silhouettes from the side, front and three-quarter views, and at the gameplay camera distance(s) the brief names. Compare with the concept silhouette (side by side, and a 50% blend, e.g. Pillow's `Image.blend`) and with existing units of other classes — classes must read apart.
4. Checkpoint: show the blockout turnaround, silhouettes and validation report. If unattended, continue and note it.

## 5. Phase 4 — Detailing from the kit

- Build every part from kit families with parameters from the spec. A missing family → add it to the kit library (parametric, reusable), not a one-off mesh.
- Detail hierarchy for a hangar close-up: macro (plates, volumes) → medium (panel splits, actuators, vents, hatches, hydraulic lines) → micro (bolts, grilles, small hatches, cable clamps). Micro detail never compensates for a weak silhouette.
- LODs are generated, not decimated: every kit script takes `--detail 0|1|2`. LOD0 everything; LOD1 without micro; LOD2 macro volumes only. Hard-surface decimation destroys bevels.
- Bevels and weighted normals on all hard edges; apply booleans; no n-gon artefacts on curved surfaces.
- Parts stay separate objects parented to their bone. Never merge the machine into one mesh: animation and damage need the parts.
- Each part is one connected island unless the custom property `max_islands` says otherwise.
- Re-run `validate.py` after detailing: added details often create new collisions at extreme poses.

## 6. Phase 5 — Materials and paint

- Material presets shared by all units: painted armour, bare metal, dark metal/frames, rubber, hydraulics/chrome, glass, emissive sensors. Values from the design language.
- Masks baked in Blender (Cycles bake, headless): ambient occlusion and an edge/curvature mask, into vertex colours or small per-unit mask textures. The engine material uses them for wear, dirt and edge highlights.
- Paint schemes are data (`paint_schemes` in the spec): base, secondary, accent, optional camo pattern, unit number, insignia. Applied through material parameters and decals, so new schemes need no new geometry.
- Decals (numbers, hazard stripes, insignia) as separate decal meshes or engine decals, never painted into geometry.
- For `hangar` quality, check close-ups under studio light: no stretched UVs, no visible gaps between plates, no empty flat areas larger than the design language allows.

## 7. Phase 6 — Review loop

Each iteration (up to `max_iterations`):
1. Render a turntable (8 angles), the concept angle, a hangar close-up set (studio 3-point light + neutral HDRI) and gameplay-distance shots.
2. Make sheets: concept vs render; this unit next to 2–3 existing units.
3. Spawn a FRESH blind reviewer (a subagent, or a separate session when the tool has none) with only the concept/turnaround, the design-language section and the renders (A/B blind when comparing two versions). It scores 1–5: silhouette, proportions, engineering plausibility, detail hierarchy, style consistency with existing units, material read, hangar close-up quality, readability at gameplay distance — and lists the top 3 problems.
4. Fix the top problems, re-run `validate.py`, record the iteration (commit when the Git rules allow). Keep or revert by evidence.

Never claim a match without renders you looked at.

## 8. Phase 7 — Export

- GLB per LOD (or one GLB with LOD nodes, following the engine's convention): metres, Y-up, applied transforms, armature included, parts as separate meshes parented to bones, `export_apply=True`.
- Naming: bones `<region>[_L|_R]`; parts `<location>__<part>[_L|_R]`; sockets `socket_<hardpoint>`; effects `fx_<kind>_<id>`; cameras `cam_<view>`.
- Engine check: import the GLB in the project's engine, place it in a test scene next to an environment scale reference, capture hangar and gameplay views.

## 9. Contract for other skills

`assets/units/<id>/contract.json`, generated from the spec and the final file:
- bones: name, parent, rest transform, ROM per axis, joint type;
- parts: name, bone, location tag, function, contact flag, approximate mass;
- sockets: hardpoints (type, size), fx sockets, cameras;
- dimensions, mass, centre of mass at rest, ground contacts;
- LOD files and triangle counts; paint schemes.

Animation tooling reads bones, ROM and contacts. Damage tooling reads location tags, parts and fx sockets. Keep the contract stable: rename only with a migration note.

Update `docs/art/units.md` (status, thumbnail, files).

## 10. Profiles

Each profile defines the skeleton template, mandatory motions (test poses / sweeps) and typical concept errors.

**walker** — sub-types biped, reverse-joint (digitigrade), quad, hexapod.
- Skeleton: root → pelvis → torso (twist) → arms/weapon mounts, head/cockpit; legs hip (3 DOF) → knee → ankle (2 DOF) → toes optional.
- Motions: stride both sides, crouch with flat feet, step-up (one leg raised ~0.5 m), full torso twist sweep, arms raised/forward.
- Ground check on; support margin in every pose.
- Typical errors: knees that cannot bend past ~20°, thigh armour fused to the pelvis, flat single-plate feet on a heavy machine, decorative gears, arms that collide with the torso when it twists.

**tracked** — tanks, tracked artillery, APCs.
- Skeleton: root → hull → turret (yaw) → mantlet/gun (pitch); road wheels and sprockets as bones (spin, suspension travel).
- Motions: full turret sweep 360° at max depression and max elevation (two sweeps with a base `pose` holding the gun), suspension compression per side (test poses with `loc` on the wheel bones).
- Tracks: separate part on the hull, UV-scroll friendly; wheels touch the track run.
- Typical errors: gun hitting the hull or engine deck when traversing at depression, turret wider than the ring allows, wheels floating above the track.

**wheeled** — trucks, buggies, wheeled APCs.
- Skeleton: root → body → axles/wheel hubs (spin, steer on steering axles, suspension travel) → turret if any.
- Motions: full steering lock both sides with suspension compressed (test poses combining `rot` and `loc`), turret sweep.
- Typical errors: wheels clipping fenders at lock, no visible suspension, wheels too small for the mass.

**hover** — hovercraft, hover tanks.
- Skeleton: root → body → fans/nozzles (tilt) → turret.
- Ground check off (the profile default); test nozzle tilt range with sweeps. Skirt clearance is not checked by `validate.py`: measure it in a side render and record it in the review.
- Typical errors: no visible lift source, nozzles that cannot tilt.

**rotorcraft** — helicopters, gunships.
- Skeleton: root → fuselage → main rotor hub (spin) → blades; tail rotor; landing gear (optional retract); weapon pylons.
- Motions: rotor sweep (blade clearance from tail boom and pylons, with flapping angle), gear down.
- Ground check only in a gear-down pose: `ground_check_poses: [gear_down]`.
- Typical errors: blades intersecting the tail boom, pylons inside the rotor disc, landing gear that cannot carry the mass.

**fixed_wing** — aircraft, VTOL, aerodyne dropships.
- Skeleton: root → fuselage → control surfaces (ailerons, elevators, rudder), VTOL nacelles (tilt), gear, bay doors.
- Motions: control surface extremes, nacelle tilt full range, gear down, bay doors open.
- Typical errors: nacelles colliding with wings when tilted, gear doors larger than their bays.

**static** — turrets, emplacements, towers.
- Skeleton: root → base → yaw ring → pitch cradle → barrels.
- Motions: full yaw sweep at min and max pitch (two sweeps with a base `pose` on the pitch cradle).
- Typical errors: barrels hitting the base at depression, no ammo feed or power access.

## 11. Constraints

- Model only: no animation clips, no damage states, no environment.
- Everything regenerable from spec + kit scripts; no manual-only Blender steps.
- Deterministic builds (`--seed`), one recorded state per phase (see Git).
- No image-to-3D geometry in the final model.
- Do not lower test thresholds to make a unit pass: change the design or the spec, and record why.

## 12. Templates

### validate.py

Run headless from the project root: `blender -b assets/units/<id>/<id>.blend --python-exit-code 1 --python .claude/skills/machine-builder/scripts/validate.py -- --spec assets/units/<id>/spec.yaml --out assets/units/<id>/validation.json` (or copy it to `tools/blender/units/validate.py`). It exits 1 when any check fails and on any error (bad spec, unknown bone, missing armature); it deletes the old report first and then always writes one, with `"passed": false` on errors.

Pose values are `[x, y, z]` rotations in degrees, or `{rot: [x, y, z], loc: [x, y, z]}` for translations such as suspension travel. A sweep may carry a base `pose` applied before the swept bone (a turret sweep at full depression). `ground_check_poses` limits the support check to the named poses.

Mark ground-contact parts with the custom property `contact = True`; optional part properties are `density` (default 1.0) and `max_islands` (default 1).

Checks: per test pose and sweep step, collisions between parts not on the same or directly connected bones (except `allowed_contacts`), the centre of mass over the support polygon of the contact parts by `min_support_margin_m`, and no non-contact part below the contacts, when the ground check applies; statically, triangles against `budgets.tris_lod0`, extra islands per part, missing `socket_<hardpoint>` objects and meshes not parented to bones.
